# 第四阶段：自动校验、导读生成与精修保护

**目标**：确保所有章节完成、字数达标、全书设定与专有名词前后闭环一致，并在完稿或精修时支持高转化导读（楔子）与合并单文件同步。

---

## 校验流程

### 1. 初始化校验

读取 `02-写作计划.json`，将项目 `status` 更新为 `"validating"`。

> 若为子Agent并行/Teams 模式，先确认各批次的状态与章节摘要已合并回 `02-写作计划.json` 和 `99-章节摘要.md`（未合并则先合并），并对每个批次接缝做衔接检查。

### 2. 逐章字数与全书一致性检查

对每一章执行以下检查：

1. **文件存在性**：检查 `filePath` 指定的文件是否存在
2. **字数检查**：使用脚本批量检查（`{skillBaseDir}` 为 skill 安装根目录，见 [shared-infrastructure.md](shared-infrastructure.md)）：
   ```bash
   python {skillBaseDir}/scripts/check_chapter_wordcount.py --all <项目文件夹路径> --json
   ```
   退出码：0=全部达标，1=有不达标，2=错误。从 `--json` 输出的 `results[]` 读取各章 `word_count` 与 `status`
   > **番茄短故事（2.5万+中短篇）字数底线**：若项目定位为番茄短故事（2.5万～4万字中短篇，走番茄「短故事」通道），全书总字数必须 **≥ 25000 字**。
3. **全书设定与专有名词闭环体检（必检项）**：
   - **核心因果源头统一**：核对开头、中段与结尾对同一核心事件（如“三年之约”是由母亲临终发誓还是外公逼迫、二十年前旧恩情是借车还是救命）的叙述是否 100% 统一。
   - **角色权势与时间线逻辑**：检查男主/大佬角色的行动逻辑是否自洽（例如：权势滔天的男主不应出现“找了三年才找到女主”或“断香三天就头痛欲裂却硬疼了三年”的漏洞，应闭环为“留下的余香省着用撑了三年刚见底，且下山第三个月就查到下落，只因尊重女主因果约定而克制守候至期满才登门”）。
   - **人物姓氏与器物名统一**：全局搜索排查是否有手误姓氏（如把“周家”写成“宋家”）或混入旧版/他版废稿的器物名称（如全书是“宋代天青釉残盏/沉香木珠”，某处误残留“定窑白釉残洗/檀木佛珠”）。
   - **医学与专业常识**：剔除违背基本常识的设定（如“难产拖延导致终身血崩后遗症”等伪科学表述）。
4. **更新 JSON**：将 `wordCount` 和 `wordCountPass` 写入对应章节记录

### 3. 汇总结果

- **全部通过**（所有章节文件存在且 `wordCountPass == true`，且全书一致性体检无硬伤）→ 更新项目 `status` 为 `"completed"`，进入步骤5
- **有不通过** → 进入步骤4

### 4. 自动修复（最多3轮）

对每个不通过的章节：

1. 将 `status` 设为 `"failed"`，`retryCount` 加 1
2. 回到第三阶段对该章节执行逐章创作流程（写前分析→撰写→润色→收尾）
3. 重写完成后重新检查字数与设定一致性
4. 更新 `02-写作计划.json`

循环规则：
- 最多执行 **3轮** 校验-修复循环
- 超过3次仍不合格的章节，保留记录但不阻塞流程
- 所有修复完成后更新项目 `status` 为 `"completed"`

### 5. 完稿交付、导读（楔子）生成与后期精修规范

#### 5.1 吸睛导读（楔子）生成规范
当用户要求添加引言/导读/楔子，或为番茄短故事生成开篇导读时，在第 1 章正上方生成 **250～400 字的高转化【楔子（导读）】**，结构包含四层钩子：
1. **开篇强冲突**：一句话点明期满之日/决裂现场（如退婚书、断亲书拍在脸上，反派嫌弃主角并强索遗物/秘方）。
2. **主角冷淡反击**：主角不哭不闹、当场签字断亲/泼茶算账的飒爽姿态。
3. **马甲/底牌反差**：连用三个排比句揭露反派引以为傲的富贵、核心专利与救命丹药全靠主角暗中托举，点出主角的双重顶级宗师身份。
4. **大佬男主登场钩子**：前脚刚算清旧账，后脚顶级权贵男主携重礼登门甘当学徒/看大门，附上男主最具苏感的表白台词收尾。

#### 5.2 用户手改稿防覆盖保护铁律（后期打磨/局部修改必守）
在完稿后的打磨、精修阶段，用户极可能直接在单文件短篇/合并单文件（如 `{小说名称}.md` / `番茄版.md`）或分章文件中手工逐句精修。此时 Agent 必须严格遵守：
1. **先读后改，以当前磁盘状态为准**：任何修改前必须先用 `Read` 工具读取目标文件的最新内容，确认用户手改过的字句。
2. **严禁运行全量覆盖脚本**：一旦用户开始手工精修合并文件（如 `番茄版.md`），**绝对禁止**再运行“从分章文件重新拼接覆盖合并文件”的脚本，否则会导致用户心血被删！
3. **精准局部替换（`StrReplace`）**：只对用户指定需要修改的段落或指定锚点句子之后的内容使用 `StrReplace`，用户声明“这段话之前不要改”的区域必须一字不动。
4. **逆向同步回分章文件**：在合并单文件上完成局部修改或用户确认精修完成后，应从合并单文件提取各章最新正文，逆向同步更新到分章文件（如 `正文/第XX章-*.md` 或 `番茄版/第XX章-*.md`），保持两边 100% 一致。

### 6. 完成报告

向用户展示创作完成总结：

```
📊 《[小说名称]》创作完成

总章数：[X] 章
总字数：[X] 字
完成率：[X]%

各章节状态：
✅ 第1章：[标题]（[字数]字）
✅ 第2章：[标题]（[字数]字）
...

项目文件夹：./小说/[小说名称]/（多章模式正文位于 ./小说/[小说名称]/正文/，单文件短篇直接位于 ./小说/[小说名称]/[小说名称].md）
```

如有不合格章节（超过3次重写仍未通过），在报告中标注：
```
⚠️ 第X章：字数不足（[实际字数]/3000），已重试3次
```
