# 第四阶段：自动校验、导读生成与精修保护

**目标**：确保所有章节完成、字数达标（论坛体除外）、全书通过「十项创作与审校自查铁律」及设定/专有名词闭环体检，并在完稿或精修阶段支持高转化导读（楔子）生成与用户手改稿防覆盖保护。全程校验与自动修复无需向用户请求确认。

---

## 1. 初始化校验

读取 `02-写作计划.json`，将项目 `status` 更新为 `"validating"`。

> 若为子Agent并行/Teams 模式，先确认各批次的状态与章节摘要已保存至 `02-写作计划.json` 和 `99-章节摘要.md`，并对每个批次接缝做衔接检查（读前批末章结尾 + 后批首章开头，断裂处轻量修顺）。

## 2. 脚本校验与全书十项自查体检

### 2.1 脚本状态与字数校验

按 skill 安装目录的绝对路径调用：

```bash
node "{skillBaseDir}/scripts/validate_project.mjs" "{项目目录绝对路径}" --json
```

脚本按计划逐章检查状态，调用原字数脚本读取正文并统计，字数口径不变，下限取本书 `minWordsPerChapter`（缺省 3000；**纯正论坛体 `forum-style` 模式无字数上下限要求**；`maxWordsPerChapter` 有值时同步校验上限）。
> **番茄短故事（2.5万+中短篇）字数底线**：若项目定位为番茄短故事（2.5万～4万字中短篇，走番茄「短故事」通道），全书实测总字数必须 **≥ 25000 字**。

脚本回填每章 `wordCount`、`wordCountPass`、`validation`（本次结论、问题类型和时间），保留原章节 `status`、`retryCount` 及其他字段；不新增 `lastError`。重复校验不增加修复次数。

| 类型 | 处理建议 |
|---|---|
| STATUS_NOT_FINAL | 核对实际完成情况，补齐未完成步骤和状态，不直接重写已有有效正文 |
| CHAPTER_FAILED | 核实原执行结果并处理失败原因，不能仅凭字数达标清除失败 |
| WORD_COUNT_LOW | 保留已有正文，按文风和扩充指南定向扩充 |
| WORD_COUNT_HIGH | 精简冗余过渡与重复描写，收束至约定字数上限内 |
| READ_ERROR | 解决读取或脚本执行问题后复检，不按零字扩充或重写正文 |

读取失败时字数与通过标记设为 null，校验结论为 error；这是脚本错误。JSON 的 `tasks` 按章合并失败类型、动作建议和实测证据。退出码：0=全部通过，1=校验未通过，2=读取或脚本错误。计划损坏等无法校验的错误直接返回 error，不覆盖计划。

### 2.2 全书十项自查与设定闭环体检（必检项）

在脚本校验基础上，对全书正文做跨章节闭环抽检与全局搜索排查：
1. **是否有逻辑谬误（含因果源头与姓氏/器物统一）**：核对全书开头、中段与结尾对同一核心事件（如誓约起因、旧恩情源头）叙述是否一致；全局排查人物姓氏手误或混入废稿器物名；核查医学/专业常识无伪科学硬伤。
2. **是否可以让读者代入**：检查关键转折与高潮章节的情绪铺垫是否到位、主角利害得失是否清晰。
3. **是否有违禁词**：全局检索并替换平台审核敏感词、涉罪违规词与红线表述。
4. **是否能在200字内吸引读者往下阅读**：重点检查第 1 章及各章前 200 字是否直入冲突或悬念钩子。
5. **是否用重复性描述词**：全局检索高频口头禅式形容词与神态词，清理跨章跨段重复描述。
6. **是否有不知所云、晦涩难懂的自创名词**：剔除生造黑话与晦涩伪概念词。
7. **是否有经典AI用句，记得好好说话**：全局检索清除“然而/与此同时/不禁/油然而生/这一刻/仿佛/不是A而是B/没有A没有B”、刻意硬凹对称的口号式伪金句（如“先XX，再XX。”“向来只XX，从不XX。”“只XX，不XX。”“A归A，B归B”“在我的字典/账本里……”）及解释性、防御性旁白。
8. **是否有过于精确、不必要的数字描写**：全局排查具体年龄与反直觉精确数字（精确百分比、寸数、度数、米数等）。
9. **是否详略得当，没有无意义的描写**：删改注水寒暄与无效环境堆砌。
10. **是否有不符合人设的情节或降智情节**：核查权贵/高智商角色与反派的行动逻辑是否匹配其人设与智商上限。

## 3. 汇总与修复派遣

- 全部章节状态为 `completed`、字数达标且十项自查无硬伤：将项目设为 `"completed"`，进入步骤 5。
- 有未通过项：
  - 若为子Agent并行/Teams 模式，主 Agent 将各章的 `tasks` 派回原写作 worker（原 worker 无法继续时新建 worker 接收相同上下文；同一章问题合并为一次任务）。派遣时给 worker：项目及章节路径、失败类型、实际/要求字数、动作建议、`chapter-checklist.md` 及适用的文风/写作指南。
  - 若为串行模式，主 Agent 直接按修复范式对未通过章节定向修复。

**修复范式：**

> 先核实问题，再执行建议动作。仅处理本章必要步骤，不机械重跑整章创作；可读取必要前后文，不修改其他章节。实际处理时将本章设为 `in_progress`，完成后设 `completed`，未解决则设 `failed`。用 Edit 更新自己章节的记录，冲突时报错后重读再 Edit。每次创作修复尝试结束后将本章 `retryCount` 加 1，成功失败均计一次；单纯复检、读取故障处理不计创作次数。返回处理结果、改动文件、检查结果和剩余问题，不向用户提问。

## 4. 最多三轮修复

首次校验后，每轮只处理未通过项；修复后调用脚本复检全书，已通过的章节不重复返工。全书最多执行 **3 轮** 修复循环。

三轮后仍未通过：将项目设为 `"needs_attention"`，保留校验标注，如实报告未通过章节或脚本问题，结束本轮执行（不能标 `completed`，也不保持为 `validating`）。

## 5. 完稿交付、导读（楔子）生成与后期精修规范

### 5.1 吸睛导读（楔子）生成规范
当用户要求添加引言/导读/楔子，或为番茄短故事生成开篇导读时，生成 **200～400 字的高转化【楔子（导读）】**（同样严格遵守前 200 字抓人、无违禁词、无AI腔、无生硬精确数字），结构包含四层钩子：
1. **开篇强冲突**：一句话点明决裂现场、核心危机或极致错位处境。
2. **主角清醒反差**：主角不哭不闹、反套路应对或暗中掌局的鲜活姿态。
3. **底牌/错位爽点**：亮出信息差、马甲反差或规则漏洞带来的高密度爽感预期。
4. **修罗场/高潮悬念钩子**：抛出最具张力的名场面悬念或代表性台词收尾。

### 5.2 番茄短篇/中篇作者书评（100～300字）可选生成规范
当作品属于**短篇或中篇**（如单篇短篇、12000字爆款短篇、10章精品中短篇、20章中篇等）且**投稿番茄小说**时：
1. **选项触发与执行时机**：
   - 若 `02-写作计划.json` 中 `generateBookReview` 为 `true`（用户在第一阶段已勾选需要），在完稿阶段直接生成书评并创建 `./小说/{小说名称}/书评.md` 存入项目文件夹，在完稿报告中一并告知路径；
   - 若 `generateBookReview` 为 `null` 或未询问过（例如用户跳过前期问答直接开写，或完稿时才说明投稿番茄），在输出完成报告后使用 `AskQuestion` 提供选项询问：「是否需要生成一个 100～300 字的番茄书评（作者自评）？」（选项：`需要` / `不需要`），用户选「需要」后同样创建 `./小说/{小说名称}/书评.md` 放入项目文件夹；
   - 若用户已明确选择 `false`（不需要），则不再重复打扰。
2. **书评内容与字数硬性标准**：
   - **字数区间**：严格控制在 **100～300 字**以内（不少于 100 字，不超过 300 字）；
   - **作者自评口吻**：以作者本人在评论区置顶自评/打五星的口吻撰写，自然接地气、好好说人话，严禁出现 AI 套话、生硬书面总结腔或策划黑话；
   - **高转化看点提炼**：用两三句话讲清主角清醒讨喜的人设、核心反套路爽点/笑点以及轻松解压的阅读体验，结尾自然招呼读者留言互动；
   - **交付方式**：勾选「需要」后，统一在小说项目文件夹下创建独立的 `书评.md`（路径：`./小说/{小说名称}/书评.md`）保存书评内容（除非用户临时明确要求仅在对话框发送）。

### 5.3 用户手改稿防覆盖保护铁律（后期打磨/局部修改必守）
在完稿后的打磨、精修阶段，用户极可能直接在单文件短篇/合并单文件（如 `{小说名称}.md` / `番茄版.md`）或分章文件中手工逐句精修。此时 Agent 必须严格遵守：
1. **先读后改，以当前磁盘状态为准**：任何修改前必须先用 `Read` 工具读取目标文件的最新内容，确认用户手改过的字句。
2. **严禁运行全量覆盖脚本**：一旦用户开始手工精修合并文件（如 `番茄版.md`），**绝对禁止**再运行“从分章文件重新拼接覆盖合并文件”的脚本，否则会导致用户心血被删！
3. **精准局部替换（`StrReplace`）**：只对用户指定需要修改的段落或指定锚点句子之后的内容使用 `StrReplace`，用户声明“这段话之前不要改”的区域必须一字不动。
4. **逆向同步回分章文件**：在合并单文件上完成局部修改或用户确认精修完成后，应从合并单文件提取各章最新正文，逆向同步更新到分章文件（如 `正文/第XX章-*.md`），保持两边 100% 一致。

## 6. 完成报告

全部通过时，将作品信息追加到 `user-preferences.json` 的 `creationHistory`，向用户展示创作完成总结：

```
📊 《[小说名称]》创作完成

总章数：[X] 章
实测总字数：[X] 字
十项自查体检：全部通过

各章节状态：
✅ 第1章：[标题]（[字数]字）
✅ 第2章：[标题]（[字数]字）
...

项目文件夹：./小说/[小说名称]/（多章模式正文位于 ./小说/[小说名称]/正文/，单文件短篇直接位于 ./小说/[小说名称]/[小说名称].md）
```

仍有未通过问题（`needs_attention`）时，如实报告“待处理”、具体章节失败类型及已执行轮次，不宣称完稿；后续恢复时从校验和未通过项继续。
